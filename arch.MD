Atom / zero-trust-proxy — Architecture
1. High-Level Overview
Atom is a zero-trust service mesh proxy: a single enforcement point that every inter-service HTTP call must pass through, cryptographically verifying caller identity and evaluating multiple independent security policies before allowing any request to reach its destination. It solves the problem of implicit network trust in microservice architectures — the assumption that a service is legitimate simply because a request originated inside the same network — by requiring every service-to-service call to prove who it is, prove it's authorized, and pass behavioral and contextual checks, on every single request, with no exceptions for "internal" traffic.

2. Component Breakdown
zero-trust-proxy/ — the enforcement layer itself. An Express.js application (proxy/index.js) that issues short-lived JWTs, runs every routed request through a five-stage middleware chain, and forwards permitted requests to their destination. Sits in front of four dummy services (services/user-service, payment-service, db-service, notification-service), each a minimal Express app simulating a real internal API. The mesh topology — service names, secret sources, target URLs, RBAC policy, allowed regions — is defined in mesh.config.json and loaded by config/load-mesh-config.js. Everything runs on plain Node.js (jsonwebtoken for JWT signing/verification, no other security frameworks).

attack-stimulator/ — a standalone Node.js script (simulate-attack.js) with zero dependencies beyond native fetch. It doesn't import any proxy code — it only calls the proxy's real HTTP endpoints exactly as any legitimate or malicious caller would, driving six stages: baseline traffic, an unauthorized-access attempt, a rapid fan-out pattern, a request flood, a region-violation-triggered reauth flow, and a final summary pulled from the proxy's own /metrics and /alerts. It connects to the proxy purely as an HTTP client — no shared code, no special access.

frontend/ — a Next.js (App Router) dashboard. Two components talk directly to the live proxy over plain fetch: HowItWorks.tsx drives an interactive Request Simulator that calls POST /auth/token and GET /route/:target/* for real, decodes the returned JWT client-side for display, and renders the actual checkpoint outcome pulled from GET /logs; LiveMetricsChart.tsx polls /metrics, /logs, and /alerts every 4 seconds and renders them as a rolling time series with Recharts. Nothing in either component is mocked — every number displayed came from a real proxy response in that browser session.

mcp-server/ — an MCP (Model Context Protocol) server built on @modelcontextprotocol/sdk, using stdio transport, exposing five tools that let an MCP-compatible client (e.g. Claude Desktop) query and operate the mesh: get_proxy_metrics, get_security_alerts, explain_request_decision, check_rbac_policy, and run_attack_simulation (which spawns attack-stimulator/simulate-attack.js as a child process and returns its full output). Like the frontend, it's just an HTTP client of the proxy's existing endpoints — it adds no new proxy-side capability, only a different interface onto the same live data.

All four components are independent processes that communicate exclusively over HTTP, using the proxy's public endpoints as the sole integration surface — none of them import each other's code.

3. Request Lifecycle, Step by Step
This is the exact, verified sequence for a call from one service to another through the proxy (e.g. user-service calling payment-service), based on the real registration order in proxy/index.js:


app.all(
  "/route/:targetService/*",
  verifyMiddleware,
  rbacMiddleware,
  lateralMovementMiddleware,
  contextMiddleware,
  rateLimitMiddleware,
  async (req, res) => { /* forward or reject */ }
);
Step 0 — Token acquisition (before any proxied call). The calling service sends POST /auth/token with { "service": "user-service" }. The proxy checks the name is registered (hasIdentity), then calls issueToken, which signs a JWT — payload { service, iat, jti }, jti a random 16-byte hex nonce — with user-service's own secret, expiring in 60 seconds. This token is returned to the caller and attached as Authorization: Bearer <token> on the actual request.

Step 1 — verifyMiddleware. The very first line records a high-resolution start timestamp (process.hrtime.bigint()) — this is the checkpoint-latency measurement's start boundary. It extracts the Authorization header; if missing or malformed, the request is rejected 401 and logged as blocked_identity. Otherwise it calls verifyToken, which (a) decodes the JWT without verifying, purely to read the claimed service name, (b) looks up that claimed service's own secret from the registry, then (c) verifies the token's signature and expiry against that specific secret. If verification fails for any reason (expired, tampered, wrong signature), the request is rejected 401. On success, req.callerIdentity is set and a req.logEntry accumulator is seeded — every later middleware refines this same object rather than creating a new log entry.

Step 2 — rbacMiddleware. Runs only if identity passed, so it can trust req.callerIdentity.service. Calls isAllowed(caller, target) against the static RBAC map. If the caller isn't in the allow-list for this target, the request is rejected 403 and logged blocked_rbac.

Step 3 — lateralMovementMiddleware. Runs only on RBAC-permitted calls (an already-blocked call never reaches here). Checks the calling service's rolling history for two independent behavioral signals: novel_target (first time this caller has ever reached this specific target) and rapid_fanout (caller has hit 2+ distinct targets within a 5-second window — threshold deliberately set to 2, not 3, because with this demo's 4-service RBAC map no caller is ever legitimately permitted to reach more than 2 distinct targets, so a threshold of 3 would make the signal unreachable through real traffic). This checkpoint never blocks — it only sets an X-Security-Alert response header, pushes an entry to the in-memory alerts array, and annotates req.logEntry.securityAlert. The request always proceeds to the next middleware regardless of what it finds.

Step 4 — contextMiddleware. Evaluates three independent, stateless properties of the request itself: time window (checkTimeWindow, based on ALLOWED_HOURS_START/END env vars, default wide open 0–24), region (checkGeo, checked against region read from the X-Simulated-Region header, defaulting to "US" if absent), and payload size (checkPayloadSize, measured from the actual parsed JSON body via Buffer.byteLength, not a client-supplied Content-Length header). If any fail, the proxy does not hard-reject — it responds 428 Precondition Required with { reauth_required: true, reason } and logs reauth_required. The proxy itself is stateless about retries; per the calling service's own contract (see Section 5), the caller is expected to fetch a fresh token and retry exactly once, and only treat a second 428 as a hard failure.

Step 5 — rateLimitMiddleware. The final checkpoint. Calls checkRateLimit(caller) against a per-service fixed-window counter (RATE_LIMIT_MAX requests per RATE_LIMIT_WINDOW_MS milliseconds, default 20/10s), keyed by verified service identity (not IP — IP is meaningless here since all traffic originates from known containers). If the caller has exceeded its window, the request is rejected 429 with a retryAfterMs hint, logged blocked_rate_limit. No automatic retry is offered or expected.

Step 6 — Forwarding (final route handler). If every checkpoint passed, checkpointLatencyMs is computed here — elapsedMs(req._startTime), i.e. the total time from the first line of verifyMiddleware to this exact point, deliberately excluding the downstream network call about to happen. The target service's URL is looked up in SERVICE_HOSTS (loaded from mesh.config.json); if unknown, it's a routing error (400, still logged as "allowed" since every security checkpoint passed — this is not a security decision). Otherwise the proxy performs the actual fetch() to the target and relays its response verbatim, logging decision: "allowed" with the checkpoint-only latency captured earlier (the downstream fetch time is never counted).

Logging, throughout. Exactly one addEntry() call fires per request — from whichever middleware ultimately rejects it, or from the final handler on success — writing a single structured entry (timestamp, caller, target, decision, reason, securityAlert, latencyMs) to an in-memory array capped at 500 entries.

4. Identity & Cryptography Model
Secret generation and isolation. Each of the four services has its own 32-byte-hex secret, one per service, stored as an environment variable (USER_SERVICE_SECRET, etc.) and injected via each service's own isolated .env file — a service only has its own secret in its environment, never any other service's. mesh.config.json doesn't store secret values at all, only the name of the env var that holds each one (secretEnv), so the config file itself is safe to commit. The proxy's identity registry (auth/identity-registry.js) reads all four secrets from its own environment (since the proxy is the only party that ever needs to verify against every service's secret) and holds them in an in-memory REGISTRY map, keyed by service name.

Token issuance (auth/issue-token.js). issueToken(serviceName) looks up that service's secret, builds a payload { service, iat, jti } (jti is a random 16-byte hex nonce, giving each token a unique identifier even if issued in the same second), and signs it with jsonwebtoken's jwt.sign, using HS256 (the library default) and a 60-second expiry (TOKEN_TTL_SECONDS).

Token verification (auth/verify-token.js) — the anti-forgery mechanism. This is the core of the identity model, and it works in two distinct steps:

Decode without verifying (jwt.decode, not jwt.verify) — this reads the payload, including the claimed service field, without checking the signature at all. This claimed identity is explicitly untrusted at this point.
Verify against that claimed service's own secret — the code looks up the secret belonging to whatever service the token claims to be, then calls jwt.verify(token, secret) using that specific secret.
The reason this prevents token forgery/relabeling: if an attacker takes a token legitimately issued to db-service and edits the payload to claim service: "payment-service" (hoping to be treated as a more-privileged caller), the verification step will look up payment-service's secret — a completely different value than the one db-service's token was actually signed with — and the signature check will fail, because a JWT's signature is a cryptographic function of both the payload and the specific secret used to sign it. Editing the claimed service name doesn't change which secret produced the original signature; it only changes which secret the verifier now checks against, guaranteeing a mismatch unless the attacker also happens to possess the target service's actual secret (in which case they wouldn't need to forge anything — they'd already have that service's real credentials). This is what the code comment describes directly: "a token signed with service A's secret cannot be validated as service B... because the signature check below always re-derives the expected secret from the registry."

5. Configuration Model
How mesh.config.json works. A single JSON file at the project root, loaded once at startup by every module that needs mesh topology (auth/identity-registry.js, policy/rbac-map.js, policy/context-policy.js, proxy/index.js) via config/load-mesh-config.js. It declares, per service, secretEnv (which env var holds its secret), url (default target URL), and optionally urlEnv (an env var that overrides url — used to inject container DNS names under docker-compose/k8s without touching the JSON). It also declares the rbac allow-list and allowedRegions array. The loader validates the file's shape at load time — every RBAC entry must reference a service actually declared in services, every service needs both secretEnv and url, allowedRegions must be a non-empty array — and throws a specific, readable error immediately if any of that is violated, rather than proceeding with a partially-broken config.

What happens if it's missing — confirmed, not assumed. I read config/load-mesh-config.js directly: loadMeshConfig() calls fs.readFileSync(configPath, ...) inside a try/catch that, on failure, throws a new error ("failed to read mesh config at '...': ..."). There is no fallback to a built-in/default in-memory config anywhere in this function or anywhere else in the codebase. If the file genuinely can't be found (and MESH_CONFIG_PATH isn't pointing somewhere valid), the process crashes at startup with a clear error rather than silently running with partial or default configuration. This is a deliberate fail-fast design choice, documented in the proxy's README. In practice this rarely surfaces because mesh.config.json is baked directly into the Docker image (COPY mesh.config.json ./mesh.config.json in the Dockerfile) — there is always a config file present unless someone explicitly overrides MESH_CONFIG_PATH to a bad path.

What a service needs to implement to integrate. Verified directly against services/user-service/index.js's real callThroughProxy function — this isn't a theoretical contract, it's the exact pattern already running: (1) POST {PROXY_URL}/auth/token with { service: <own-name> } to get a token; (2) attach it as Authorization: Bearer <token> on the actual call, routed through {PROXY_URL}/route/<target>/<path> rather than called directly; (3) on 428, fetch a fresh token and retry exactly once — if the retry also comes back 428, treat it as a hard failure (403) rather than looping, since the proxy itself has no memory of retry attempts; (4) on 429, do not retry automatically — the response's retryAfterMs is a hint, not an instruction to auto-retry.

6. Data Flow for Observability
Every request's outcome flows through exactly one path: whichever middleware terminates the request (or the final forwarding handler) calls addEntry() in logs/request-log.js, appending one structured record — timestamp, caller, target, decision, reason, securityAlert, latencyMs — to an in-memory array capped at 500 entries. lateralMovementMiddleware additionally pushes to its own separate in-memory alerts array (module-local to lateral-movement-middleware.js) whenever a behavioral signal fires, independent of whether the underlying request ultimately succeeds or fails downstream.

Three read-only GET endpoints expose this same data: /logs (optionally filtered by ?service= or ?decision=, most-recent-first, capped to 100 results per call), /alerts (the full alerts array), and /metrics (aggregate avgMs/maxMs/minMs/p95Ms/sampleSize, computed live from the last 100 log entries' latencyMs values via getLatencyMetrics()).

Both the frontend and the MCP server are independent, unprivileged HTTP clients of these same three endpoints — neither has any special access, and neither talks to the other. LiveMetricsChart.tsx polls all three every 4 seconds client-side and renders a rolling 30-point time series. HowItWorks.tsx's Result Panel calls /logs?service=<caller> after sending a live request and finds the matching entry by caller+target. The MCP server's get_proxy_metrics, get_security_alerts, and explain_request_decision tools call /metrics, /alerts, and /logs?service= respectively — the same requests a curl command or the frontend would make, just wrapped in tool definitions an AI client can invoke. Because all three consumers hit the same live in-memory state, an alert or log entry produced by one (e.g. a request sent from the frontend's Request Simulator) is immediately visible to the others (e.g. queryable moments later via an MCP tool call) — there is no synchronization step because there is only one source of truth.

7. What's Demo-Specific vs. Production-Ready
Genuinely reusable via config, not hardcoded: service names, their secret-env-var names, target URLs (with DNS-name override support), the RBAC allow-list, and the allowed-regions list — all of this now lives in mesh.config.json and can be changed without touching proxy code, verified by re-running the full attack simulation and MCP tool suite against the refactored code with identical results to the pre-refactor version.

Hardcoded/demo-specific: the four dummy services themselves (user-service, payment-service, db-service, notification-service) exist purely to give the proxy something realistic to sit in front of — they're not meant to be production services, just fixtures. mesh.config.json's default content encodes exactly this 4-service topology; changing it to a different topology is supported by the loader, but nothing about the dummy services generalizes beyond being test fixtures.

Known simplification, explicitly not production-ready: the context-policy geo check (checkGeo in policy/context-policy.js) determines a request's region from a client-supplied X-Simulated-Region header, defaulting to "US" if absent. This is intentional for local demo/testing — it's what lets attack-stimulator/simulate-attack.js deterministically trigger a region violation without real geolocation infrastructure — but it means the check trusts caller-supplied input for a security decision, which is trivially bypassable by any caller that simply doesn't send an inaccurate header. A production deployment would need to derive region from something the caller can't control: IP-based geolocation performed by the proxy itself, or a header set by infrastructure outside the caller's control (e.g. a CDN/load-balancer's CF-IPCountry-style header), not a header the request itself supplies. This limitation is documented directly in zero-trust-proxy/README.md, not hidden.

Also worth being explicit about (not asked for directly, but relevant to "production-ready"): the in-memory logs/alerts/rate-limit state is per-process and non-persistent — a proxy restart loses all history, and the design doesn't support running multiple proxy replicas behind a load balancer without shared state (rate limits and lateral-movement history would fragment per-instance). This is standard for a demo/reference implementation and not something the config externalization work touched.
