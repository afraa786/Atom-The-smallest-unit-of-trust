1. At the center of this system sits a single lightweight Express-based proxy running on port 4000, which acts as the mandatory checkpoint for every internal API call in the mesh. Rather than allowing microservices to call one another directly over their own ports, all inter-service communication is rerouted through a unified path /route/:targetService/* so that no request, regardless of source or destination, can bypass inspection. Three dummy services (user-service, payment-service, and db-service) simulate a realistic internal topology, each running independently on its own port and container, but each has had its direct-call logic stripped out entirely in favor of routing every outbound request through the proxy first. This design mirrors how a real service mesh sidecar or API gateway would sit transparently between services in a production multi-cloud environment, ensuring that lateral movement between compromised nodes is structurally impossible without passing through the enforcement layer.

2. Identity in this system is established cryptographically rather than by network location or shared secrets. Each service is provisioned with its own unique 32-byte secret at startup, generated via Node's crypto module and injected through an isolated per-service .env file critically, no service has access to any other service's credential, mirroring a real zero-trust posture where compromise of one node should never grant visibility into another's identity material. A central identity registry on the proxy maps each service name to its corresponding secret, but this registry is used only for verification purposes, never for issuing a shared or universal key. This asymmetric, per-service secret design is what allows the system to later prove, under test, that a token signed by one service's key can never be successfully verified, tampered, or relabeled as belonging to another service.

3. Authentication flows through short-lived JSON Web Tokens rather than long-lived credentials or session state. Before making any outbound call, a service first requests a token from the proxy's /auth/token endpoint, presenting only its own name; the proxy looks up that service's secret, signs a JWT containing the service name, issued-at timestamp, and a random nonce, and returns it with a 60-second expiry window. This token is then attached as a Bearer credential on the actual outbound request. When the proxy receives that request at its routing endpoint, it does not simply validate the token against a shared key it first decodes the unverified claim to determine which service the token purports to represent, then re-verifies the signature specifically against that claimed service's registered secret. This two-step decode-then-verify process is what closes the gap that a naive single-shared-secret JWT implementation would leave open, and it has been explicitly tested against token tampering, signature corruption, and expiry edge cases, all of which correctly result in immediate rejection before any request reaches its target.

4. Passing identity verification is treated as necessary but not sufficient for authorization a second, independent layer of role-based access control governs which verified identities are actually permitted to reach which destinations. This is implemented as an explicit policy map defining allowed communication paths (for example, user-service may call payment-service, and payment-service may call db-service, but user-service is explicitly forbidden from calling db-service directly, even while holding a completely valid, correctly-signed token). This separation of concerns identity verification answering "who are you," and RBAC separately answering "are you allowed to do this" is deliberate, and it has been proven under test by demonstrating that a fully authenticated, cryptographically valid request from user-service targeting db-service is still rejected with a 403, purely on authorization grounds, independent of the identity layer succeeding.

5. Beyond static authentication and authorization, the proxy is designed to reason about behavioral context on every request rather than treating a single successful check as permanent trust. Contextual policy checks evaluate factors such as request timing windows, origin characteristics, and payload size anomalies, and rather than issuing a hard block when something looks irregular, the system is designed to force a re-authentication challenge requiring the calling service to obtain a fresh, freshly-verified token before the request can proceed, rather than assuming a previously valid identity remains trustworthy indefinitely. Layered on top of this, the proxy tracks each service's historical calling pattern to detect lateral movement flagging and blocking cases where a service suddenly attempts to reach a target it has never communicated with before, or attempts multiple distinct services within an abnormally short window, which is the exact behavioral signature of a compromised node attempting to pivot. Every decision made at any of these layers, whether an allow, a block, or a forced re-authentication, is logged with full reasoning and timestamped for auditability, and the time added by the proxy's own verification pipeline is measured independently of downstream network latency, keeping enforcement overhead within the sub-15-millisecond target even as multiple layers of cryptographic and policy checking run on every single request.
